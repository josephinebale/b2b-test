## Routing

Custom hash router (`src/lib/router.ts`): `href`, `navigate`, `useHashRoute`, `canonicalPath`. `navigate` writes the hash and then calls every `useHashRoute` subscriber **in the same tick**. The browser fires `hashchange` in a later task, so without that a caller which changes node state and navigates in one handler commits a render carrying the new node and the old route. That is what made the header nav paint a frame with no active tab while entering a location.

## Booking request flow

Entry: **Request booking** (`PageHeading`) → `#/request-booking`.

1. **Location, date and time** — a location **dropdown** containing only the active persona’s organisation, already set to the current location. Changing it updates the breadcrumb and the worker list. Continue needs a date and an end time after start. Frequency: one-off / weekly / fortnightly. The location’s **service type** is shown under the dropdown. **Who the booking covers** depends on type (see below). A SIL house does not nominate residents per shift.
2. **Details** — support description, “I’ll share all relevant support plans…”, driving radios. Optional **finance reference** only for a **centre / day program**, where the claim divisor depends on who attended. It is not shown for SIL or home and community, and participants never carry a balance.
3. **Select workers** — Workers with the requested date and time applied. `requestWorkerTiers` starts from the same location-relative populations as Workers and removes provider-history workers who overlap a confirmed Hireup booking. Requested and ended bookings do not block availability.

   Tier 1 (**Your location team**) appears first, followed by tier 2 (**Worked elsewhere in Northern Sydney**). Unavailable people are omitted rather than shown disabled. Both tiers show provider hours, support plan status, and medication and driving assessments. Tier 1 relies on its heading instead of repeating “Known at [location]” on every row. Tier 2 also retains the locations and completed-shift counts that make cross-location judgement possible. Fatigue remains a separate conditional tag. The richer moderator variant adds suburb, distance, and platform-held training without replacing this baseline evidence.

   Tier 3 (**Available nearby**) appears only when both earlier tiers are empty. Its explanation says nobody known to the location or grouping is available for that time. Nearby rows remain selectable and provide a **Message** action using the existing Messages destination. They state only what the prototype knows: suburb, distance, no history with this provider, and support plan not shared. They do not mention induction or buddy shifts. Created-request detail preserves names selected from any tier; nearby names are plain labels because no provider-history profile exists.

   Placeholder provider-worker availability marks **2:00am–5:00am on any date** unavailable for everyone with provider history, giving research sessions a reliable way to demonstrate the fallback. At other times, confirmed Hireup booking overlaps decide availability. Changing the date or time clears any earlier selections.

   Rest signals are derived by `fatigueSignalForWorker` at render time from the worker’s current confirmed and completed bookings, plus private placeholder bookings elsewhere on the platform and any session-created bookings. The booking being displayed is excluded. Zero gap or an overlap reads **No break before shift**; a positive gap under eight hours reads **Less than 8 hours rest**. The UI receives only that derived result, never the source booking’s time, location, client, provider, or shift count. Signals appear beside available workers, while no tag is shown when the worker has at least eight hours.

How a booking expresses **participants**:

- **SIL house** — `participantIds` is every resident, the same on every shift (the roster of care is set upstream). The UI keeps this in the background: no picker on request, and booking cards / week / detail do not list residents.
- **Centre / day program** — `participantIds` is who is attending that session. The request flow has **Who is attending** checkboxes; continue needs at least one. Cards, week, and detail name the people (or “N attending” in the week grid).
- **Home and community** — `participantIds` is the one named person. Request shows that name with no picker. Cards, week, and detail show the name.

Location settings **Location name** shows service type as a read-only field. Worker tiers, site coverage, fatigue, messages, and grouping faces are unchanged: a location is still a location.

`<BookingRequest key={visibleData.location.id} />` so switching location in the request **resets the draft**.

Submit writes a `requested` booking and goes to `#/bookings/request/{id}`. Detail: status stepper, workers, pricing estimate (`$72.74` / hour, same as list cards).

**Requested** list cards use `href(/bookings/request/${booking.id})`. Confirmed cards still stay on `/bookings`.

The Bookings week schedule collapses to **4 bookings per day** with show more / Show less (`COLLAPSED_BOOKINGS_PER_DAY`). At current seeded volume no day reaches that cap, so the expander stays hidden; it still covers denser weeks and session-created requests. A day with no bookings shows **No bookings** on the same line as a card's first line of text, not above it: the label carries the card's own box (a transparent 1px border plus `.ui-inset-compact`) so it clears the same 9px a card's border and inset add. Do not centre it in the column — that dropped it below its neighbours and read as detached from the row. Every shift card is a whole-card link to `/bookings/detail/:id`; the detail adapts the existing requested-booking layout for requested, confirmed, and completed bookings. The neutral detail route keeps confirmed and ended shifts from being described as requests. Newly submitted requests still open their established `/bookings/request/:id` route.

Booking cards in the Bookings status lists and weekly schedule, plus booking detail, derive the same rest signal on every render. Cards and detail keep the booking’s own times and duration visible; the disclosure limit applies to the other work used in the calculation. Vehicle allowance is not shown on booking cards or detail. Driving required/not required remains booking support context and is separate from an allowance.

`fatigueSignalForBooking` shows the signal only while there is still a decision to make: an `ended` booking, or one whose start has already passed, returns nothing. Requested and confirmed shifts still ahead keep it. Worker selection is unaffected, because it asks about a shift that has not been created yet.

The week grid states the signal as a plain bold `text-xs` line, the same treatment the card already gives **Sleepover**, rather than as a `Tag`. `.ui-tag` is one line (`white-space: nowrap`) and `.ui-card` clips overflow, so at a seventh of the column the label lost its last word (“Less than 8 hours r”). A wrapping line fits the 112px text box in two lines at page width, and `break-words` keeps a long word from being cut in a narrow window. Tags remain correct on the wide Bookings list card and detail. Do not put the grid label back in a `Tag`, and do not loosen `.ui-tag` globally — prices and status tags depend on staying one line.

## Notifications belongs to the person

Route: `#/notifications`. Notifications is work assigned to the signed-in person, scoped to their configured entry node rather than the node they later browse to. A location-entry persona sees one supportable. A grouping-entry persona sees every unique descendant supportable in that grouping, including descendants reached through nested groupings. The scope never crosses the persona’s organisation.

Each row keeps the existing title, explanation, date, 20px lucide icon and whole-row link treatment. A multi-supportable scope adds the quiet supportable-name third line (`text-xs text-text-tertiary`) used in Messages; a single-supportable house-manager scope omits that repeated label. Selecting a row enters that supportable before opening its existing destination. Zero-count summaries do not render. The three summary types remain: unread messages → Messages, requests waiting → Requested, and bookings to approve → Ready to approve. Support-plan events are dated and worker-specific, not one aggregate row.

Four concrete event types fill gaps that have no nav count of their own:

- **[Worker] cancelled a booking** — derived from a `cancelled` booking carrying `cancelledBy` and `cancelledAt`; opens that booking’s detail. The row date is when it was cancelled; urgency order uses the affected shift’s start. Dee Why 1 / Beth C is the seeded example.
- **[Worker]’s [medication or driving] assessment has lapsed** — derived from the expiry date on the platform-held assessment; opens that worker’s profile. Dee Why 1 / Scarlett O / medication is one seeded example.
- **[Worker]’s support plan needs review** — derived from `supportPlanReviewDueAt`; opens that worker’s profile. Dee Why 1 / Erica O is one seeded example.
- **Invoice ready to approve** — derived from an invoice in `ready-for-approval`; opens the existing Invoices placeholder. North Ryde 1 is the seeded example. The invoice has no amount or funding data.

The list is organised by response urgency rather than event type or location. **Needs attention now** comes first: cancelled bookings lead because an upcoming shift has lost its worker, followed by waiting-request summaries ordered by their next shift. **Checks and approvals** follows with booking approvals, invoices, lapsed assessments, and support-plan reviews. **Messages** is last because Messages already carries its own count and destination. Each group reuses the existing section-heading plus divided-Card pattern; there is no new container style. Putting the title inside the card was tried and reverted, because it added complexity the existing tokens did not require.

It no longer counts the full review and message backlog, so the number signals immediate operational work rather than “a lot”. Sofia Patel’s seeded Careforce caseload therefore reads **16**, while all 124 unresolved items remain represented on the organised page. Research did not establish that a regional manager needs a different data scope. Wanting less region-wide traffic is treated as a future **notification preference** by person and event type, not as a narrower region boundary. Per-type preferences are not built.

### Alignment traps (do not “fix” with extra padding)

- `.ui-button--default` is **unlayered CSS**: `height: var(--control-height-default); padding: 0 var(--space-4)` (16px). The account dropdown trigger also carries the later `.header-menu-trigger`, which intentionally gives it the same 36px height and 8px horizontal padding.
- `.ui-button` already `inline-flex` + `align-items: center` + `gap: var(--space-2)`.
- **Three control heights, each named for the role it serves, and every one of them a token** (`src/index.css`): **`--control-height-field`** 40px for anything you enter or read data in — inputs and **every dropdown**; **`--control-height-default`** 36px for a standalone button, the account trigger and the default icon button; **`--control-height-small`** 32px for a repeated control in a dense list (week arrows, row actions, `ui-button--small`). Height follows the control's **role**, not whatever happens to sit near it. The one rule that outranks role: **controls in the same horizontal group match each other** — an input beside a button comes down to the button's 36px (`h-9`), not the other way round, because button height is unlayered CSS and a Tailwind height on the button is a silent no-op (the Messages search row was 40 / 36 / 28px). A mixed-height row still needs `items-center`, or stretch top-aligns it. `SectionHeadingRow` is not a horizontal group — its control aligns to the text beside it, bottom edge on the last baseline when that block has a supporting line and centred on the line when it is a title only; see **Section layout rules**. The scale does not cover native radios and checkboxes, multiline fields, whole-row targets, or content-sized cards. The week-grid expander is that last case. `tests/ui-primitives.test.ts` pins the three tokens.
- **A dropdown is a field, so it is 40px everywhere, through one class.** `.ui-select` owns height, border, radius, fill, 12px inset, 40px right inset for the chevron, sm type and the focus ring; call sites add width only. `.ui-select--clearable` is the single sanctioned variant (64px right inset) for the Bookings worker filter, which carries a clear button inboard of its chevron. Every dropdown also renders the same 20px `ChevronDown` at `right-3` — `appearance: none` removes the native arrow, so a select without one reads as dead text, which is how the Bookings worker filter shipped. There is no small select: the Overview **Sort by** control was 32px to match the week arrows in the row above it and so read as a different kind of thing to the identical filters on Bookings and Jobs to be done. A 40px control still fits that 48px heading row (it sits 3.5px below the row top instead of 11.5px) and the row does not grow. `tests/ui-primitives.test.ts` fails if any `<select>` sets its own height and padding.
- **One field label everywhere: 14px `text-sm` `font-medium` `text-text`, with `mt-1` (4px) to the field.** No size tier by surface. A 12px tier used to cover the compact filter panels (Bookings filters, Jobs to be done, Information architecture) and the Overview **Sort by**, which made an identical dropdown read as a different control depending on the screen, and left the label smaller than the 14px value inside the field it named. Density is handled by the panel's spacing, not by shrinking its labels. `tests/ui-primitives.test.ts` rejects a field label at any other size, weight or colour.
- `.header-menu-trigger` now applies only to the account menu. It supplies the 36px height, radius, 12px gap (`--space-3`), 1px `--color-border`, white fill, and subtle hover. Its 34px content box holds the **sm 28px** avatar without the border cutting through it.
- The header breadcrumb starts after a 24px gap and a 24px divider beside the logo. The logo starts at the 32px page inset and the account box ends on it, with no pull-backs.
- Badge: 18px height, `min-width: 1.125rem`, 6px horizontal padding (`calc(var(--space-1) * 1.5)`), `leading-none` / flex centre, and `tabular-nums`. Digits are already centred by the flex box — 4px padding made the pill look cramped rather than off-centre, so the fix was air, not alignment. Two digits render 27.5px wide, one digit 19.7px. Colour remains `#D6244A` (about 4.99:1 with white, so no token change was needed). Header utility badges are overlaid at the top-right with a `--border-width-focus` (2px) surface-coloured separation ring; the Bookings and Messages nav badges remain inline.
- A button uses an icon or a text label, not both, except the account menu trigger: its avatar is identity and its chevron says that a menu opens. Icon-only controls keep accessible labels. Icons stay `h-5 w-5` (20px), with two sanctioned pairings rather than a second free size. A glyph inside the 32px `size="small"` IconButton drops to `h-4 w-4` (16px) so 20px in the 36px control and 16px in the 32px one both leave exactly 8px on each side. A chevron immediately following an inline text label is also 16px, because it is a companion to the text rather than a glyph inside a control — 20px beside 14/20 type outweighs the word. `tests/icon-size.test.ts` enforces both by checking each 16px glyph really does sit inside a small IconButton or beside an inline text label, so the size cannot leak out to loose icons.
- Repeated actions in a dense list use the 32px control. The week arrows use `size="small"` and sit 8px apart. Standalone controls that are not in a list — the header utilities, the research dock, the row overflow menus on Workers and Settings — stay at 36px.
- Location marker: `h-9 w-9 rounded-lg` (28px `sm` in compact controls), no border/ring, one green for every location (`#E6F2E8` / `#216B2D`). Initials are `text-xs leading-none` — the same packed 12/12 box as the badge. The square is a fixed 28/36px flex box, not a type line, so unused 16px leading would not be a line of text; `leading-none` keeps the glyph optically centred. The breadcrumb uses the location name without a marker, so every rendered marker carries both initials.

## Visual consistency rules

### Section layout rules

Stated once so section spacing and heading rows stop being re-decided:

1. **`SectionHeadingRow`** (`src/pages/dashboard/SectionHeadingRow.tsx`) is the only way a section heading is built on the grouping Overview. **Unfilled shifts** (`BookingsNeedingAttention.tsx`), the merged direct-child location list or child groupings (`HousesAndCentresPanel.tsx`), and **Recently booked workers** (`WorkersPanel.tsx`) all render through it: `mb-3`; left — `text-md font-bold` title and optional supporting line (`mt-1 max-w-content text-sm text-text-secondary`); right — one optional aside block (`shrink-0`) for week controls, one `GroupingLocationSortControl` on the merged location list when it has two or more rows (14px **Sort by** label and the shared 40px `ui-select` on one `inline-flex items-center gap-2` line), or **View all**. The row stays `items-start` and the aside sits in **`LineAlignedControl`**. **`LineAlignedControl`** (`src/components/LineAlignedControl.tsx`, `.line-aligned` in `src/index.css`) is the **single implementation** of the line-alignment rule, and it has **two modes chosen by the text beside it**: a control aligns to the **bottom** of a block that has a bottom to align to, and to the **line itself** when the block is one line.
   - **Text block has a supporting line** (more than one rendered line): the wrapper is translated so the control's **bottom edge sits on the last line's baseline**, and a taller control grows upward. The pair finishes level — Unfilled shifts 43.5/43.5 and the location list 43.5/43.5 in a 48px row, `PageHeading` with a description 55.5/55.5 in a 60px row, worker rows 72.3/72.3 in an 88px row.
   - **Title-only block** (one rendered line): the control **centres on that line**. Bottom-aligning here misses, because the last line IS the title: **View all** landed 2px high of centre on **Recently booked workers**, and a 36px button on a title-only `PageHeading` hung 11px above the row. Centred, both land on the line's own centre — View all 12/12 in a 24px row, the Information architecture **Back** button 16/16 in a 32px row — and a control taller than the line overflows evenly instead of only upward.
   - The mode is **derived, never declared**: `textLines` counts the rendered lines of the block by grouping client rects that overlap vertically, so a badge inside a title stays part of the title's line and there is no pixel tolerance to tune. **No caller passes a mode**, and none is special-cased by name; `line`, `className` and `children` are the only props. If a caller had to say which mode it wanted, this component would be the wrong shape. Centring is also the CSS default (`--line-aligned-height`), so the pre-measurement layout is the single-line case rather than the row top.
   - Parent rows stay `items-start` and the wrapper is `overflow: visible`, so **no row grows** in either mode. Never hand-tune a margin on the control instead. **`SectionHeadingRow`**, **`PageHeading`**, and the request-booking **worker-selection rows** all use it — do not add a second wrapper on those pages. `SectionHeadingRow` asides use `--text-md--line-height`; `PageHeading` actions use `--text-xl--line-height`; worker-row checkbox and avatar use `--text-sm--line-height`. The worker-selection row still uses **16px top / 12px bottom** padding because the evidence text runs to several lines. Request-booking worker rows use **16px top / 12px bottom** padding (`pt-4 pb-3`), not `py-3`. Those rows always run to several lines, so they take the bottom-aligned mode: the 36px avatar sits 36.3px to 72.3px in an 88px row, clear of both dividers. The extra top padding keeps the name clear of the divider above while the bottom is held open by the evidence lines. Do not normalise this to `py-3`. Week controls (`WeekScheduleControls` in `BookingsWeek.tsx`) use **`--control-height-small`** (32px) — the same height as the aside **Message** / **Book** buttons (`ui-button--small`). The sort control does **not** match them: it is a dropdown, so it takes the 40px **`--control-height-field`** that every other dropdown uses; see **Alignment traps**. Two controls in different rows are not a horizontal group. Nothing on those pages positions a section heading or its control outside `SectionHeadingRow`. **Do not adjust section heading alignment by editing a page — change `SectionHeadingRow`, or leave it alone.**
2. Section heading to supporting line, and supporting line to content block, use the same values as the location Bookings week (`BookingsWeek.tsx`): **`--space-1`** (`mt-1` on the supporting line); **`--space-3`** (`mb-3` on the header row before the card or grid). Record by token name only.
3. Between sections: **`--space-6`** (32px) in the grouping Overview content column (`gap-8`); **`--space-5`** (24px) for `.layout-content-aside` column gap (`gap: var(--space-5)` / `gap-6` in Tailwind — not `gap-5`).
4. Named steps only: **`--space-1`…`--space-8`** = 4, 8, 12, 16, 24, 32, 40, 48px. Tailwind numbered utilities multiply 4px, so **`gap-6` is 24px and is not `--space-6`**.
5. A status pill on a **tinted** card inverts: dark fill, light text, so it stays readable against the tint. A status pill on a **white** card uses a light fill with dark text. Example: requested on a tan pending card uses `--color-pending` fill and `--color-surface` text (same as `StatusPill` on the location week); confirmed on white uses `--color-success-surface` fill and `--color-success` text.

### Booking card in a week grid

This anatomy has been specified and reversed more than once — **this section is the answer**, not the last instruction.

Card contents, in order:

1. **Identifying line** — worker name at a location; house or client name at a grouping (`text-xs font-bold`, left-aligned).
2. **Time** — `formatTime` range (`7:00am - 3:00pm`), left-aligned.
3. **Plain bold signal lines** when present — Sleepover, fatigue/rest signals (`text-xs font-bold`).
4. **Status pill last** — full width of the card’s content box (`flex w-full items-center justify-center`), centred text, `mt-3` below the lines above. The pill is **not** sized to its content and **not** left-aligned.

Pill colours invert against the card tone (`bookingWeekCardTone`):

- On a **tinted** card (requested → `.ui-card--pending`, cancelled → `.ui-card--attention`): **dark fill, light text**. Requested uses `bg-pending text-surface` / `--color-pending` on `--color-surface` (`StatusPill` on the location week; `.attention-grid-status-pill--pending` on the grouping attention calendar). Cancelled outreach on the grouping calendar uses `--color-badge` fill on `--color-surface` (`.attention-grid-status-pill--attention`).
- On a **white** card (confirmed, ended): **light fill, dark text** — e.g. confirmed uses `bg-success-surface text-success`.

The grouping Dashboard **Unfilled shifts** calendar uses this same anatomy. Its identifying line is the house name; its pill text states outreach state via `attentionCardSendLine` (“Not yet accepted”, “2 of 5 declined”, “Beth C cancelled”) rather than the booking status label. On the location week, **cancelled** cards omit the pill and name the canceller in plain bold text instead — the only deliberate difference.

Implementation: location week status uses `StatusPill`; grouping attention outreach uses the same layout classes with `.attention-grid-status-pill--pending` / `--attention` for inverted fills only.

- Standard page shell: 32px top padding and 24px between `PageHeading` and the first content block (`mb-6` = 6 × `--spacing` = `--space-5`). Do not use `mb-5` here: Tailwind numbered utilities are 4px steps, so `mb-5` is 20px, not `--space-5`. Do not remove page headings. At a location, Bookings has **View by status** and **Request booking** in its heading. The grouping Dashboard has no heading action. **Report incident** stays on booking cards.
- Container insets come from one three-step scale, picked by density rather than a single number everywhere. `.ui-inset-compact` (8px) is for dense data cells — the Bookings week schedule and the booking chips inside it, where seven columns share one row. `.ui-inset-row` (12px vertical, 16px horizontal) is for list rows — Workers, Messages, Notifications, Settings people, Choose location, and the nested worker card on a booking. The horizontal 16px matches the card step, so row content and card content share one left edge. `.ui-inset-card` (16px) is for cards holding prose or several blocks. Larger standalone settings sections keep their 24px inset. The shared in-progress card keeps **24px** (`.p-6` / `--space-5`) on purpose: it is a placeholder, not a prose card, and the extra air disappears with the card when `LANDING_CONTENT_ENABLED` comes on.
- One heading block per page, like Workers: title, description, and the page action inline in the same row. Bookings keeps **Bookings** as its title with **Request booking** on the right; the selected view (`activeLabel` — Confirmed, Requested, and so on) and its “Showing 1 – 40 of N …” count head the results column instead, next to the rail that changes them. Folding the view name into the page heading was tried and reverted.
- Colour signals status or interactivity. On the Bookings week schedule and the grouping Dashboard attention calendar, `bookingWeekCardTone` applies the same status rule: `requested` cards use `.ui-card--pending` because they need a decision; `cancelled` cards use `.ui-card--attention` because something has already gone wrong; `confirmed` and `ended` cards stay white with quiet status pills. Outreach state (“Not yet accepted”, “2 of 5 declined”) belongs in the send line, not the tint. This is reversed on Jobs to be done: provenance tags are coloured because that is what a reader is scanning for, and the page sits outside the signed-in product. Do not carry that exception into signed-in screens.
- Whole-surface links use the same flat interaction treatment: `ui-target-row` for stretched-link rows and `ui-linked-surface` for a link wrapping a card. Both transition only background and border colour over 150ms, use `surface-subtle` on hover and `surface-selected` while pressed, and keep the blue focus outline. Pending and attention cards mix their existing surface and border tokens on hover so the signal does not disappear. Do not add chevrons, movement, or shadows — those crowd the seven-column grid or make a data tile look like a floating overlay.
- **A clickable thing says so at rest, and how it says so depends on whether it has text of its own.** An entity name that navigates takes the link treatment through `a.ui-entity-link` — brand blue, underlined. It is keyed to the *element*, not an opt-in class, so a name that opens a profile cannot ship looking like dead text; that is exactly how the old Team list read for months while the dashboard worker list beside it was blue. Rendered `as="span"` (Settings people, Choose location, nearby workers without local profiles) it is a label and keeps the plain strong-text treatment. The Messages conversation list opts out with `a.ui-entity-link--plain`, because its name selects a conversation in the pane beside it rather than navigating and the row already carries a selected state; the opt-out matches the base rule's specificity, so it must stay **after** it in the file.
- Week-grid cards get no text cue at all. The card is one link to the booking and the worker name inside it is not separately clickable, so styling that name as a link would promise a profile and deliver a booking. The tile carries the affordance instead: `.ui-linked-surface > .ui-card--default` takes a full-strength `--color-border` at rest rather than the `--color-border-subtle` a static card uses. Hover then moves only the fill, matching how a pending card in the same grid already behaves — there is no `gray-400`, so a darker hover border would have to jump to `gray-500` and read as heavy.
- **One hover for every text link: lose the rest-state underline and deepen to `--color-brand-hover`.** All three treatments resolve to it — `.ui-link` (the standard link), `a.ui-entity-link` (a name that opens a profile), and `.ui-target-row__link--text` (a row's own link) — so hovering a link never depends on which screen it is on. Use `.ui-link` rather than hand-rolling `text-brand underline hover:text-brand-hover`; that pattern was written out longhand in seven places and six of them silently missed the hover. `.ui-link--flush` is the one variant: the week grid's expand control spans the card and sits on its bottom edge, so its focus ring is inset by `--border-width-focus` instead of outset. The week-grid expander is content-sized, not a 32/36/40 control: full-width text link, `py-3` plus a 1px top rule, which computes to 45px because of padding and type, not a fixed height. Do not force it onto the control-height scale. The class must stay **after** the shared `:focus-visible` rule to win. The footer follows it too, through `.ui-link--muted`: those links stay secondary grey rather than brand blue, but they now carry the underline at rest and lose it on hover like everything else. They previously did the exact inverse — no underline until hover — which meant hovering meant two opposite things depending on where you were on the page. The variant sets colour only, so it must stay **after** `.ui-link` to win.
- A link **nested** inside an interactive surface — currently just the worker link on a Bookings card, which opens a profile while the card opens the booking — carries `.ui-nested-link` and answers on its own. While the pointer is on it the row holds its rest state, so two destinations are never lit at once, and the link drops the underline it carries at rest and deepens to `--color-brand-hover`. Losing an underline is a change only the link can make, so it cannot be misread as the surface behind it highlighting. This is deliberately **not** applied to a link that *is* its row's own link (Workers, Notifications, the dashboard worker list): those share the row's destination and should highlight together. The suppression is written as `:not(:has(.ui-nested-link:hover))` on the row's hover and active rules rather than a background override, so it does not have to guess the row's rest colour; `.ui-target-row--active` is excluded by name rather than out-specified, so a selected row keeps its blue through hover.
- Booking prices use neutral tags, not success green. Jobs to be done is the exception: origin uses `validated` (location-marker green) and `pending` (requested-card pair). Signed-in Tag tones are `neutral`, `success`, `validated`, `pending` (still in play or running out of time), and `attention` (`#D6244A` on a light tint of it). `attention` is only for a state that has already gone wrong — today a cancelled shift — not for urgency.
- List rows keep one line: avatar, name, then row actions right-aligned and centred against the avatar.
- **A control earns an icon or a label, not both** (avatar and menu chevron exempt). Grouping Overview **Recently booked workers** rows carry text-only **Message** / **Book** secondary buttons; location Workers rows carry 32px icon-only actions with accessible labels.
- **Every icon-only button carries an outline at rest.** `.ui-icon-button` itself sets the 1px `--color-border` and white `--color-surface`, so the outline is the base rather than an opt-in prop — a new icon button cannot ship bare by leaving something off. Emphasis-per-setting was tried and abandoned: outlining only standalone controls (week arrows, research dock) while dense row actions took a grey `--subtle` fill and header utilities took no chrome at all left three resting states on one screen, and the grey fill read as a tag or a location marker rather than a control. Adjacent actions sit 8px apart. Because the class is unlayered CSS its background beats any Tailwind `bg-*` utility, so the header's selected state needs the plain `.header-utility--active` class; a utility there paints nothing. Decorative icons — the glyphs on notification summaries — stay bare `lucide` glyphs, and that contrast is now the whole tell. The account trigger is exempt because its avatar carries identity.
- Tooltips sit **under** their trigger, centred, everywhere. The moderator dock is the only exception: its tooltips flip above and anchor to their inner edge, because a centred tooltip on a corner button overhangs the viewport even while hidden and gives the page a horizontal scrollbar. `.ui-card--divided` is `overflow: visible` and rounds its own first and last rows instead (`calc(var(--radius-lg) - 1px)`, inset by the border), so a row action's tooltip can hang below the card. Do not put `overflow: hidden` back on it — that clips the tooltip, and the old workaround of flipping it to the side of the button reads as misplaced. Raising the tooltip's own `z-index` does not lift it out of its row: `.ui-target-row__action` needs `z-index: 2` to clear the stretched link, and that makes each row's actions a stacking context, so the tooltip is trapped inside it and the next row's actions paint straight over it. `.ui-target-row__action:hover, :focus-within` lifts the row being pointed at to `z-index: 3` instead. This only became visible once icon buttons gained a background — while they were transparent there was nothing to cover it.
- Rail navigation on Bookings status views and all Settings scopes uses the same active treatment: **`--border-width-rail` (4px)** body-text left marker (`.ui-rail-item`), `px-3 py-2`, quiet blue selected background (`bg-info-surface`), and **bold labels at rest**. The marker takes body text colour rather than brand blue, matching the active section underline in the header. Worker profile and the location-profile preview share `layout-rail-content` (column width, `items-start`, 24px column gap) and the 16px `.ui-rail-stack` under the rail column; they do not invent a second rail treatment. Idle hover is `bg-surface-selected`, matching Bookings.
- Dividers stay only where they separate adjacent content that would otherwise read as one group. The line above Bookings filters is intentionally absent; the rail’s 16px gap (`.ui-rail-stack`) separates navigation from filters. A line was tried under the Bookings shift actions and removed: the links still sat in open space, because a divider separates neighbours rather than attaching anything to anything. They belong to the page heading instead.
- A section heading sits above a divided Card, reusing that existing pattern rather than introducing a container style. An in-card title row was tried and reverted, because it added complexity the existing tokens did not require.

## Layout archetypes

- Page shell: 1440px (`--container-page: 90rem`), main `px-8 pt-8 pb-4`. The maximum inner width is **1376px**. The full-width seven-column schedule therefore gives each day about **196.6px nominally**, or about **196.3px inside the Card’s two 1px outer borders**.
- Narrow column: `--narrow-column-width: 20rem` (320px). Bookings status views, Settings rails, worker profile, the location-profile preview, and the Messages list all reuse it; do not invent per-page sidebar widths.
- Bookings status views + Settings use `layout-rail-content`. The default Bookings schedule has no rail. Worker profile and the location-profile preview also use that layout for a sidebar card, not destination nav.
- **The Messages list is not a rail and must not be restyled as one.** It keeps `layout-master-detail`. Sharing `--narrow-column-width` is all it shares with the five rail-content surfaces. Its rows are records, not destinations; they keep their own selected state and row treatment. Do not convert conversation rows to the 4px marker / `bg-info-surface` rail item in a later “conformance” pass.
- Messages shell is a **definite** `height: var(--messages-shell-height)` with `grid-template-rows: minmax(0, 1fr)`, and both columns carry `min-h-0`. All three are needed: with only a height the grid row still stretches to its content, and without `min-h-0` a column refuses to shrink, so the list grows instead of scrolling. Conversation rows carry the divider on the `li` with `last:border-b-0`, so the list finishes on one line rather than doubling up against the next element.
- Supportables, grouping and location Workers, and stubs use `width-main-column`, which reserves the established 320px narrow-column proportion even where the adjacent rail is absent. The grouping Dashboard does not: its content column fills the remaining space beside the aside. There is no location Dashboard.

A rail showing only the person’s working set was identified as the version that might work and has not been tried.
- A **rail is sub-navigation within a section that has more than one view of the same records**, owned by the page and rendered inside the content area below the second tier. That is already how Bookings status views and Settings work. Worker profile and the location-profile preview also use `layout-rail-content`. This is why scope cannot be a rail: the collision is five surfaces.
- The **Messages list is not a rail**. It shares `--narrow-column-width` and that is all. Its rows are records, not destinations, and they keep their own selected state and row treatment. A conversation row styled as a rail item would promise a destination and deliver a selection. Do not “finish the job” by converting it.
- **Workload per supportable is stable**; the count of supportables and groupings is what grows. The location face is therefore scale invariant, and everything at issue is the tree above it. Navigation does not solve two consequences of that growth: worker tier 2 is scoped to “the grouping” and stops meaning anything at a large one, and person-scoped Notifications has the same breadth problem the grouping Dashboard had.
- **Finding, not a decision.** Two participants at different providers hold a mistaken belief about what the platform can do. **Sufi** (Northcott; Northcott session · 30:16), asked to show how she posts a job, opens the booking request. **Suman** (Life Without Barriers; Life Without Barriers session · 32:08) says they did not know a request could go to more than a very limited number of support workers. Both are now in the jobs catalogue as reworded jobs. The gap is a wrong model of the product rather than a missing skill, which is why it is not answered by training alone.

## Settings (three scopes)

Still three destinations with a **left rail** per scope (not one dumped settings page). Routes and surviving section IDs are unchanged.

**Location settings** (`/manage-location`) uses entity-specific labels without changing its route, section IDs, structure, or stored location model.

For a house, centre, or day program, the heading remains **Location settings** and the existing language remains place-based:

- Location profile — editable worker-facing About, support locations, broad support needs, safety information, and support required; includes **Preview profile**
- Support worker preferences
- Support plan — **kept for research**. A house-level plan is likely leftover from one-client matching; ask the participant whether a SIL house has one plan or many.
- Location name — **kept for research**. Names are public CPA SIL listing names; ask whether a house manager would rename them.
- People (load-bearing for roles and access)

For a client, the page heading is **[Name] settings**. Its rail uses **[Name] profile**, **Support worker preferences**, **Support plan**, **Personal details**, and **People with access**. Profile copy uses **About [Name]**, **At home**, **Support needs**, and **Help at home**. The details card uses **[Name] details**, **Name**, and **Support type**. Support-plan and access helper text says workers are booked to support the named person rather than booked at a location. Profile preview follows the same language.

Removed from this scope: location picture (the marker is initials, no photo renders), support areas, specialised support, COVID-19.

Location profile edits persist per location in `hm.locationProfiles`. The preview deliberately uses broad location-level information only: never add resident names, diagnoses tied to individuals, private addresses, or booking-specific support-plan details.

**Organisation settings** (`/organisation-settings`): organisation details, financial details, documents, people. Whole scope is **read-only**. Financial and documents are still present (thin placeholder content).

**Your account** (`/your-account`): **Account** only. Account has an email and profile photo derived from the active persona, plus one password field. Notification preferences is recorded in TARGET-IA.md under **Still target** only — no section in the prototype. Removed: About you (no one reads a manager bio here), Privacy (no profile visibility to govern). Old paths such as `/your-account/privacy` still open the Account section.
